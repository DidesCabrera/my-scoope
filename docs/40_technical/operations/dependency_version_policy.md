# Dependency and tool version policy

Status: active
Date: 2026-10-02
Applies to: the Django backend, web frontend, Expo mobile client, and local iOS builds

## Sources of truth

- Python runtime: the version configured in CI and deployment. Python packages: the committed, exact `==` pins in `requirements*.txt` (including their transitive dependencies).
- Web JavaScript: root `package.json` and committed `package-lock.json`.
- Mobile JavaScript and native module versions: `mobile/package.json` and committed `mobile/package-lock.json`. Use `npm ci` to reproduce these versions. Expo-compatible versions must be checked before changing native packages.
- Local iOS: `mobile/ios/` is generated by Expo and ignored by Git. Its `Podfile.lock` and `Pods/` describe only the current local build; they do not define project dependency versions. Regenerate or synchronize them whenever the mobile lockfile or native configuration changes.
- Toolchain: CI specifies Node 22.14 for mobile and Python 3.13 for backend checks. Mobile requires Xcode 26.4 or newer; record the Xcode and CocoaPods versions used when diagnosing a native build failure. Do not assume a previously installed simulator app proves a fresh build works.

## Updating dependencies

1. Work on a branch based on current `staging`. Keep dependency upgrades separate from unrelated UI changes when practical.
2. Review release notes, compatibility requirements, security advisories, and the affected direct and transitive packages. Treat an Expo SDK, React Native, Django, Python, Node, or Xcode upgrade as a planned migration.
3. Change the manifest and lockfile together. For mobile, use Expo's compatibility check (`npx expo install --check`) and regenerate the npm lockfile deliberately. Do not hand-edit lockfiles or use an unreviewed bulk upgrade.
4. Validate the smallest affected surface first. JavaScript-only mobile changes use focused checks and Fast Refresh. Native dependency or configuration changes require a fresh simulator build. Backend dependency changes require the relevant backend gate. Run the full integration tier only when the change reaches its integration boundary or a critical path requires it.
5. Review the lockfile diff and record the old/new versions, the reason for the upgrade, validation performed, and any rollback constraint in the change description. Publish only the tested commit through the repository's integration workflow.

Review available security fixes promptly. Review routine dependency updates about once a month; batch compatible patch updates, and schedule major upgrades individually. Avoid changing versions solely because a newer release exists.

## Automated monitoring and review cadence

Dependabot checks Python, root npm, mobile npm, and GitHub Actions every Monday.
Routine minor and patch updates are grouped by ecosystem and proposed against
`staging`; major versions remain separate so their migration risk is visible.
Dependabot may keep at most three version-update pull requests open per configured
ecosystem. It must not merge dependency changes automatically.

Review the queue monthly and close superseded or unnecessary proposals. Handle a
critical or high vulnerability as soon as the alert arrives: confirm whether the
affected dependency is used in an exposed path, prepare the smallest safe update
from `staging`, and run the validation layer that owns the risk. Lower-severity
alerts may join the monthly review when the affected path is not exposed and that
decision is recorded. A green Dependabot pull request is evidence from CI, not
approval to merge.

Dependabot alerts are a repository setting on GitHub. Keep them enabled, along
with security-alert notifications for repository maintainers. Do not enable
Dependabot security-update pull requests while `staging` remains the integration
branch: GitHub creates those fixes against the default branch and would bypass
the repository workflow. Apply an actionable alert on a branch based on current
`staging` instead. The committed `.github/dependabot.yml` controls scheduled
version proposals; it does not by itself enable GitHub security alerts.

## Repairing a stale local iOS build

If Expo reports that `pod install` cannot resolve a local Expo pod, compare the versions in `mobile/ios/Podfile.lock` and `mobile/node_modules`. A local podspec mismatch after `npm ci` or a branch change indicates stale generated iOS state.

From `mobile/ios`, run `pod update --no-repo-update` to synchronize the generated Pods with the versions already installed from `mobile/package-lock.json`. Then run `pod install --deployment` to confirm the snapshot is internally consistent and `npm run ios:staging` from `mobile` to verify compilation and launch. This repairs local generated files; it is not a project-wide dependency upgrade. If it fails, inspect the exact CocoaPods error and the relevant Expo release guidance before deleting generated files or updating package versions. Do not routinely run `pod install --repo-update` for this local mismatch.

CI's mobile checks validate JavaScript and the web bundle on Linux. They do not compile iOS. Record a successful native build as separate evidence when native versions change.
